Самостоятельно размещённый пул работает на сервере **.113** (`tomni-proxmox-113`). С 2026-10-18 каждый
раннер OmniRoute имеет **одну роль**, одну метку и бюджет памяти/ЦП, соответствующий измеренной
нагрузке. Слот Turbopack получает столько ресурсов, сколько требуется сборке; остальные слоты рассчитаны
с учётом измеренных пиков. Переподписка ресурсов на сервере возникает только тогда, когда сборка Turbopack
совпадает со сборкой webpack Release-Green и заданием lint; это компенсирует swap хоста (16 GB), а поскольку
сборки pull request выполняются на размещённых раннерах, большую часть времени слот Turbopack простаивает:

| раннер               | метка            | роль                                                                                                                                               | `MemoryHigh` / `MemoryMax` | `CPUQuota`        |
| -------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | ----------------- |
| `omniroute-113-5`    | `omni-build`     | Сборки Turbopack: `ci.yml` `Build` (только push/dispatch), Docker amd64, `npm-publish`, `nightly-v4-build`, `preview-artifact`, ночная сборка a11y | 56 GB / 60 GB (swap 0)     | 1600 %            |
| `omniroute-113-6`    | `omni-release`   | Release-Green (`release-green` + `main-green`), сборка webpack                                                                                     | 20 GB / 24 GB (swap 4 GB)  | 800 %             |
| `omniroute-113-2`    | `omni-light`     | ночные задания (Schemathesis, promptfoo, garak, k6, запуск a11y) и `quality.yml` `lint-guard`                                                      | 12 GB / 16 GB (swap 4 GB)  | 600 %             |
| `omniroute-113`      | `omni-light`     | тот же пул, что и выше                                                                                                                             | 8 GB / 12 GB               | 400 %             |
| OmniHeuris, OmniMind | (их репозитории) | только Dependabot (пиковое потребление каждого — 155 MB, 2026-10-18)                                                                               | 4 GB / 6 GB                | 200 % для каждого |

Измерено 2026-10-18:

| ресурс    | значение                           | значение для планирования                                                                                                                                                                                                                                                                                                                                                                             |
| --------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RAM / CPU | **78 GB / 32 ядра**                | пиковое потребление production-сборки Turbopack без ограничений составило 49 GB (`tests/unit/ci-build-bundler-webpack.test.ts`); в Next 16.3.8 одна только фаза компиляции занимает ~40 GB (36 GB RSS в `next-build` плюс 17 воркеров загрузчика по 3 GB, измерено 2026-10-18); сборка webpack — ~14–16 GB. Одна сборка Turbopack и одна сборка webpack помещаются вместе; две сборки Turbopack — нет |
| swap      | 16 GB                              | `omniroute-113-5` работает с отключённым swap (`MemorySwapMax=0`), поэтому вышедшая из-под контроля сборка завершается при достижении лимита, а не заставляет весь сервер использовать swap                                                                                                                                                                                                           |
| `/tmp`    | **12 GB tmpfs = RAM**              | всё размещённое там занимает память; остаточные файлы удаляются через 3 ч                                                                                                                                                                                                                                                                                                                             |
| CPU       | наблюдалась нагрузка 60 на 32 ядра | до введения квот одна сборка Turbopack (~1166 % CPU) вместе с набором тестов покрытия на том же сервере лишала heartbeat-сигналы других слушателей ресурсов (`The self-hosted runner lost communication`, #16853)                                                                                                                                                                                     |
| раннеры   | **6 слушателей**                   | 4 OmniRoute + OmniHeuris + OmniMind; `omniroute-113-3/-4/-7/-8` отключены (`systemctl enable --now` повторно включает один из них)                                                                                                                                                                                                                                                                    |

Ограничения находятся в файле `/etc/systemd/system/actions.runner.<…>.service.d/override.conf`
каждого юнита (предыдущие значения сохранены как `override.conf.bak-20261018`) и были применены
без остановки с помощью `systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` —
без перезапуска, поэтому выполнявшиеся задания не были затронуты. Метки изменяются через API раннеров
(`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`), также без остановки.

## Установка janitor (однократно, на сервере)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): каждые 30 минут, журнал в /var/log/runner-janitor.log
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` обязателен: перед удалением janitor с помощью одного снимка открытых
файлов убеждается, что путь не используется, а без этого инструмента ничего не
удаляет и сообщает об этом (exit 1). Сначала проверяйте любые изменения с
`--dry-run` — этот режим точно показывает, что будет сделано, не изменяя ничего.

Что происходит при каждом запуске: удаляются оставшиеся после наших процессов
объекты (`runner-*`, `omniroute-*`, `next-build*`, `e2e-build.tar.gz`) через **3 ч
на tmpfs** и через 24 ч на диске в `_work/_temp`; завершается `next-build` старше
75 мин (ни одна задача не выполняется так долго — 2026-08-27 одна из них
проработала 70 мин после того, как GitHub объявил её потерянной); удаляются
рабочие копии старше 48 ч для раннеров, чьи юниты **остановлены**; выдаются
предупреждения при заполнении диска ≥ 85 %, PSI памяти `full/avg60` ≥ 10 % и
количестве слушателей, превышающем `MAX_ACTIVE_RUNNERS` (с разбивкой на
omniroute/прочие). Exit 1 = требуется внимание; прочитайте журнал.

Правило 75 минут не обнаруживает сборку, от которой GitHub уже отказался. Когда
`Runner.Listener` не может продлить задачу, в `_diag/Runner_*.log` появляется
`POST request to …/renewjob timed out after 100 seconds`, API сообщает, что задача `completed`
(с ошибкой), примерно через десять минут после последнего успешного продления, а `next-build`
продолжает работать без привязанной задачи (2026-10-18: сборка #17066 завершилась с ошибкой
в 19:43, но через пять минут её процесс сборки всё ещё занимал 40 GB). Проверьте ref в новейшем
`_diag/Worker_*.log`, затем отправьте SIGTERM только дереву процессов сборки по PID —
`next-build`, `npm run build`, `build-next-isolated.mjs` и рабочим процессам `_work`.
Никогда не трогайте `Runner.Listener`, `RunnerService.js` или `Runner.Worker`: рабочий
процесс сообщает, что задача отменена, а слушатель самостоятельно возвращается в онлайн.

## Юниты раннеров: KillMode

Значение `KillMode=process` по умолчанию для раннера оставляет цепочку
`Runner.Worker → npm → next-build` работающей после остановки или перезапуска
юнита — осиротевшая сборка продолжает потреблять оперативную память и ЦП без
привязанной задачи. У каждого юнита OmniRoute есть дополнительный файл
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
с `KillMode=mixed`: сначала SIGTERM отправляется слушателю, а при достижении
`TimeoutStop` всему cgroup отправляется SIGKILL. Изменение вступает в силу при
следующем перезапуске юнита — перезапускайте **по одному раннеру за раз и только
когда он простаивает**, выполняя проверку простоя и перезапуск одной командой.

## Правила эксплуатации

- **Одновременно выполняется только одна сборка Turbopack — это обеспечивается меткой.** Каждое задание, запускающее полный Turbopack
  `next build`, нацелено на `[self-hosted, omni-build]`, и только **`omniroute-113-5`** имеет эту
  метку: `ci.yml` `Build`, `npm-publish.yml` `publish`, `nightly-v4-build`, `preview-artifact`,
  ночная a11y-сборка (#16853) и **amd64** в `docker-publish.yml` (webpack внутри BuildKit —
  Turbopack там аварийно завершился, запуск 33253576569). Ветка Docker для arm64 остаётся на `ubuntu-24.04-arm`.
  amd64 в `docker-publish` использует ту же группу параллелизма `heavy-build-main`, что и `Build`
  в `ci.yml` (`cancel-in-progress: false`). Docker Engine должен находиться на `omniroute-113-5`. Второй слот Turbopack
  не помещается в 78 GB (2 × 33–37 GB плюс всё остальное на машине); второй слот безопасен только для
  сборок webpack.
- **Сборки pull request выполняются на хостинговых раннерах (2026-10-18).** `Build` в `ci.yml` попадает на `omni-build` только для
  `push` и `workflow_dispatch`; `Build` для каждого `pull_request` (из этого же репозитория или форка) и `merge_group`
  выполняется на `ubuntu-latest` с webpack. Когда каждый PR из этого же репозитория направлялся в этот слот, сборка Turbopack
  занимала его на 29–58 мин, 18 сборок ожидали в очереди до 18 ч, а push-сборка самой релизной ветки
  получила слот лишь один раз за 40 заданий. На хостинговом раннере та же сборка PR занимает 8–12 мин параллельно с другими
  заданиями PR. Turbopack — сборщик, поставляемый через `npm-publish`, — продолжает проверяться в релизной ветке
  ночной a11y-сборкой ветки по умолчанию (04:41 UTC), каждой push- или dispatch-сборкой,
  достигающей слота, и самим `npm-publish`. `tests/unit/build/heavy-build-queue.test.ts`
  фиксирует это условие из четырёх частей.
- **Никогда не выделяйте слоту Turbopack меньше измеренного необходимого объёма.** 2026-10-18 в 18:06 лимиты слота были
  снижены с 56G/60G до 40G/44G, чтобы освободить место для `omni-release`. Фаза компиляции провела
  весь запуск на уровне `MemoryHigh` (memory PSI `full` 30–43 %), а `Runner.Listener`, использующий
  ту же cgroup, не смог продлить своё задание. Заданные владельцем 56G/60G от 2026-10-17 были восстановлены
  в тот же день. При значениях ниже этих сборка не завершается с ошибкой — она начинает буксовать, и задание теряется.
- **У Release-Green есть собственный слот (2026-10-18).** До этого обе проверки Release-Green выполнялись
  на `omni-build`: при каждом push (~10/час, за один день 97 из 100 push-запусков были отменены в процессе работы)
  и во время трёх полных прогонов длительностью около 2 ч в день (прогон в 05:29 ждал слот 6 ч) — единственный слот сборки
  был многократно перегружен, а сборки PR из этого же репозитория ждали часами.
  `release-green` и `main-green` теперь нацелены на `omni-release` (только `omniroute-113-6`) с
  `OMNIROUTE_USE_TURBOPACK=0`, и начавшийся запуск больше не отменяется новым push (при этом
  ожидающий слот по-прежнему схлопывает поток запусков). `tests/unit/build/runner-capacity-routing.test.ts`
  фиксирует маршрутизацию, переключение на webpack и то, что на `omni-release` ничего не собирается с Turbopack.
- **Лёгкий пул: `omni-light`.** `omniroute-113` и `omniroute-113-2` выполняют ночные задания, которым нужна
  только серверная сборка `next build` (~5–6 GB; webpack), а также `lint-guard` из `quality.yml`. У `omniroute-113`
  до 2026-10-18 было `MemoryHigh=4G` — сборка promptfoo 54 минуты с трудом продвигалась из-за освобождения памяти;
  8 GB устраняют троттлинг.
- **Меньше слушателей — намеренно.** Четыре юнита OmniRoute были отключены 2026-08-29 — каждый дополнительный
  слушатель становится ещё одним потребителем описанного выше бюджета памяти. Лимит уборщика — 6 (`MAX_ACTIVE_RUNNERS=6` в cron): он учитывает
  каждый `Runner.Listener` на машине, а OmniHeuris и OmniMind добавляют ещё два к нашим четырём.
- **Никогда не очищайте `/tmp` или `_work` вручную, пока занят хотя бы один раннер.**
  Проверка с последующим удалением и паузой между ними привела к тому, что активное задание `Build` потеряло свой
  `_work` 2026-08-27. Уборщик выполняет проверку и удаление за один шаг;
  предоставьте это ему.
- Остановка раннера во время задания отменяет задание (наблюдалось в рабочей среде): выполняйте `systemctl stop`, только
  если у его слушателя нет дочернего процесса `Runner.Worker`, — и делайте это одной командой.
- Рабочие процессы не должны размещать артефакты в `/tmp` (он находится в RAM). Скачивайте в
  `$RUNNER_TEMP` (на диске, отдельно для каждого раннера) — артефакт `next-build` объёмом 1.3 GB загружался на tmpfs 27–32
  минуты, тогда как загрузка с диска заняла 2 минуты.
- VPS `.15` предназначен только для омологации и никогда не запускает CI-раннеры.

## Размещённая среда (раннеры GitHub-hosted)

Учётная запись использует план **Pro**: **40 одновременно выполняемых размещённых заданий**, общих для всех проверок PR,
всех рабочих процессов, запускаемых при push, и стандартной конфигурации CodeQL. По результатам измерений 2026-10-18 во время
серии слияний (~10 слияний в час в `release/v3.8.52`): за 24 ч было создано **2 500 запусков рабочих процессов**,
за 6 ч выполнено 44 push в ветку, **106 размещённых заданий поставлены в очередь**, в то время как проверки PR ожидали
часами, а PR сливались без них. При каждом push в ветку запускались девять рабочих процессов:

| при каждом push в `release/v*`              | размещённые задания | результат при пиковой нагрузке                                       | с 2026-10-18                                                                         |
| ------------------------------------------- | ------------------: | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `ci.yml` (полная матрица)                   |               до 30 | отменены следующим push, 24 из 24 за день                            | не запускается при push в `release/**` (запуск PR + Release-Green)                   |
| `quality.yml`                               |                  ~6 | отменены, 23 из 23                                                   | не запускается при push в `release/**`                                               |
| `Release-Green` `--quick`                   |                   0 | выполнялся на `omni-build`, отменены 97 из 100                       | слот `omni-release`, никогда не отменяется, ожидающие запуски объединяются           |
| `Lock released branch`, `OpenSSF Scorecard` |                   2 | один запуск в очереди на каждый push                                 | один запуск на ref (`tests/unit/build/hosted-lane-concurrency.test.ts`)              |
| `Release acceptance` (теневой отчёт)        |                   1 | один размещённый `npm ci` на каждый push, никогда не отменяется      | без изменений — кандидат на фильтр `paths:`                                          |
| `Publish to Docker Hub` → `Deploy to VPS`   |                   2 | отменяются при каждом push; ветвь amd64 конкурирует на `omni-build`  | без изменений — канал развёртывания владельца                                        |
| стандартная конфигурация CodeQL (`dynamic`) |                   4 | `javascript-typescript`, `actions`, `c-cpp`, `python` на каждый push | без изменений — Settings → Code security; `c-cpp`/`python` здесь ничего не сканируют |

`tests/unit/build/push-storm-diet.test.ts` фиксирует триггер только для push в `main` для `ci.yml` и
`quality.yml`. Побочный эффект: Codecov больше не получает базовую выгрузку при каждом push в release-ветку (этот
шаг носит информационный характер и использует `continue-on-error`); встроенная в репозиторий проверка покрытия и комментарий к PR

**Дополнительные собственные мощности не устранят очередь размещённых заданий.** Devbox
(`devbox-vm-06-dev002`, 24 vCPU / 54 ГБ) мог бы разместить раннер, но сессии агентов уже
поддерживают нагрузку на уровне 20–26, в контейнере агента отсутствует демон Docker, а перегружена именно
размещённая среда. На машине `.113` в тот же момент было свободно 71 ГБ, а нагрузка составляла 5–8; её ограничивает
указанный выше бюджет памяти на каждый listener (не более 6 listener), а не CPU. Оставшиеся меры
связаны с процессом: проводить PR серии слияний через очередь Mergify (`label=queue`; пакеты используют
один общий запуск CI `merge_group` вместо одного запуска на каждый PR плюс одного на каждый push), сократить набор языков
в стандартной конфигурации CodeQL и фильтровать `release-acceptance.yml` по файлам, которые он читает.
