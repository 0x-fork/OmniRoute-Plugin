## janitor स्थापित करा (फक्त एकदा, सर्व्हरवर)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): दर 30 मिनिटांनी, /var/log/runner-janitor.log मध्ये लॉग करा
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` आवश्यक आहे: एखादा पाथ निष्क्रिय असल्याची खात्री janitor तो काढून टाकण्यापूर्वी
उघड्या फाइल्सचा एक snapshot घेऊन करतो; हे साधन उपलब्ध नसल्यास तो काहीही काढून टाकत नाही आणि तसे
सांगतो (exit 1). कोणताही बदल आधी `--dry-run` वापरून तपासा — तो नेमके काय करेल हे दाखवतो
आणि कशालाही स्पर्श करत नाही.

प्रत्येक रनमध्ये तो काय करतो: **tmpfs वर 3 तासांनंतर** आणि डिस्कवरील
`_work/_temp` मध्ये 24 तासांनंतर आमचे स्वतःचे उरलेले घटक (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) साफ करतो; 75 मिनिटांपेक्षा जुना `next-build` बंद
करतो (कोणतेही job इतका वेळ चालत नाही — 2026-08-27 रोजी GitHub ने त्याचे job हरवलेले
घोषित केल्यानंतर एक build 70 मिनिटे चालला होता); ज्यांची unit **थांबलेली** आहे अशा
runners चे 48 तास जुने checkouts काढून टाकतो; तसेच डिस्क ≥ 85 %, memory PSI
`full/avg60` ≥ 10 %, आणि listeners ची संख्या `MAX_ACTIVE_RUNNERS` पेक्षा जास्त असल्यास
(omniroute/other तपशीलासह) सूचना देतो. Exit 1 = लक्ष देणे आवश्यक; लॉग वाचा.

GitHub ने आधीच सोडून दिलेला build 75-मिनिटांच्या नियमात सापडत नाही. जेव्हा
`Runner.Listener` त्याचे job renew करू शकत नाही, तेव्हा `_diag/Runner_*.log` मध्ये
`POST request to …/renewjob timed out after 100 seconds` दिसते, शेवटच्या यशस्वी renewal नंतर
सुमारे दहा मिनिटांनी API त्या job ला `completed` (failure) म्हणून नोंदवते आणि कोणतेही job
जोडलेले नसताना `next-build` चालूच राहतो (2026-10-18: #17066 चा Build 19:43 वाजता failed
झाला होता आणि पाच मिनिटांनंतरही त्याचा build 40 GB व्यापून होता). सर्वात नवीन
`_diag/Worker_*.log` मध्ये ref ची खात्री करा, त्यानंतर फक्त build tree ला PID द्वारे
SIGTERM पाठवा — `next-build`, `npm run build`, `build-next-isolated.mjs` आणि `_work`
workers. `Runner.Listener`, `RunnerService.js` किंवा `Runner.Worker` यांना कधीही स्पर्श
करू नका: worker job cancelled म्हणून नोंदवतो आणि listener आपोआप पुन्हा online होतो.

## Runner units: KillMode

Runner चे डीफॉल्ट `KillMode=process`, unit थांबवली किंवा restart केली असता
`Runner.Worker → npm → next-build` चालूच ठेवते — कोणतेही job जोडलेले नसताना अनाथ build
RAM आणि CPU वापरत राहतो. प्रत्येक OmniRoute unit मध्ये
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
येथे `KillMode=mixed` असलेले drop-in आहे: प्रथम listener ला SIGTERM आणि
`TimeoutStop` वेळी संपूर्ण cgroup ला SIGKILL. ते unit च्या पुढील restart वेळी प्रभावी
होते — निष्क्रियतेची तपासणी आणि restart एकाच command मध्ये ठेवून, **एकावेळी फक्त एक
runner आणि तो निष्क्रिय असतानाच** restart करा.

## कार्यपद्धतीचे नियम

- **एका वेळी फक्त एक Turbopack बिल्ड — लेबलद्वारे सक्तीने लागू.** पूर्ण Turbopack
  `next build` चालवणारे प्रत्येक जॉब `[self-hosted, omni-build]` ला लक्ष्य करते आणि केवळ **`omniroute-113-5`** कडे ते
  लेबल आहे: `ci.yml` मधील `Build`, `npm-publish.yml` मधील `publish`, `nightly-v4-build`, `preview-artifact`,
  रात्रीचे a11y बिल्ड (#16853) आणि `docker-publish.yml` चे **amd64** (BuildKit मधील webpack —
  तेथे Turbopack पॅनिक झाले, रन 33253576569). arm64 Docker टप्पा `ubuntu-24.04-arm` वरच राहतो.
  `docker-publish` चे amd64, `ci.yml` मधील `Build` सोबत `heavy-build-main` concurrency गट शेअर करते
  (`cancel-in-progress: false`). Docker Engine `omniroute-113-5` वर असणे आवश्यक आहे. दुसऱ्या Turbopack
  स्लॉटसाठी 78 GB पुरेसे नाहीत (2 × 33–37 GB आणि उर्वरित मशीनचा वापर); दुसरा स्लॉट फक्त
  webpack बिल्डसाठी सुरक्षित आहे.
- **Pull-request Builds होस्टेड वातावरणात चालतात (2026-10-18).** `ci.yml` मधील `Build` केवळ
  `push` आणि `workflow_dispatch` साठी `omni-build` पर्यंत पोहोचते; प्रत्येक `pull_request` (स्वतःच्या origin मधील किंवा fork मधील) आणि `merge_group` Build
  webpack सह `ubuntu-latest` वर चालते. स्वतःच्या origin मधील प्रत्येक PR स्लॉटकडे वळवल्यामुळे, एका Turbopack
  Build ने तो 29–58 मिनिटे व्यापून ठेवला, 18 Builds कमाल 18 तास रांगेत राहिले आणि रिलीज शाखेच्या स्वतःच्या push Build ला
  40 जॉबमध्ये फक्त एकदा स्लॉट मिळाला. होस्टेड वातावरणात त्याच PR Build ला PR च्या इतर
  जॉबच्या जोडीने 8–12 मिनिटे लागतात. `npm-publish` ज्या बंडलरसह वितरित होते ते Turbopack, रिलीज शाखेवर
  डीफॉल्ट शाखेच्या रात्रीच्या a11y बिल्डद्वारे (04:41 UTC), स्लॉटपर्यंत पोहोचणाऱ्या
  प्रत्येक push किंवा dispatch Build द्वारे आणि स्वतः `npm-publish` द्वारे सतत वापरून तपासले जाते.
  `tests/unit/build/heavy-build-queue.test.ts` चार-अटींचे गेट निश्चित करते.
- **Turbopack स्लॉटचा आकार त्याच्या मोजलेल्या गरजेपेक्षा कधीही कमी करू नका.** 2026-10-18 रोजी 18:06 वाजता
  `omni-release` साठी जागा करण्याकरिता स्लॉट 56G/60G वरून 40G/44G पर्यंत कमी करण्यात आला. संपूर्ण रनदरम्यान
  compile टप्पा `MemoryHigh` वरच राहिला (memory PSI `full` 30–43 %), आणि त्याच
  cgroup मध्ये असलेले `Runner.Listener` आपला जॉब नूतनीकृत करू शकले नाही. 2026-10-17 रोजी मालकाने ठेवलेले 56G/60G
  त्याच दिवशी पूर्ववत करण्यात आले. या मूल्यापेक्षा कमी आकारात बिल्ड अयशस्वी होत नाही; ते सतत संसाधनांसाठी झगडत राहते
  आणि जॉब हरवतो.
- **Release-Green चा स्वतःचा स्लॉट आहे (2026-10-18).** तोपर्यंत Release-Green ची दोन्ही प्रमाणीकरणे
