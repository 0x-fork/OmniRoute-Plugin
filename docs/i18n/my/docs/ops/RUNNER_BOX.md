## janitor ကို ထည့်သွင်းခြင်း (တစ်ကြိမ်သာ၊ စက်ပေါ်တွင်)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): မိနစ် 30 တိုင်း လုပ်ဆောင်ပြီး /var/log/runner-janitor.log သို့ log ရေးရန်
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` လိုအပ်သည်။ janitor သည် path တစ်ခုကို မဖယ်ရှားမီ ဖွင့်ထားသော
ဖိုင်များ၏ snapshot တစ်ခုဖြင့် ၎င်း path ကို အသုံးမပြုနေကြောင်း အတည်ပြုသည်။ ထို tool မရှိပါက
မည်သည့်အရာကိုမျှ ဖယ်ရှားမည်မဟုတ်ဘဲ ထိုအကြောင်းကို အသိပေးမည်
(exit 1)။ ပြောင်းလဲမှုတိုင်းကို `--dry-run` ဖြင့် ဦးစွာ စမ်းသပ်ပါ — ၎င်းသည်
မည်သည့်အရာကို လုပ်ဆောင်မည်ကို အတိအကျ ပြသပြီး မည်သည့်အရာကိုမျှ ထိတွေ့ပြောင်းလဲမည်မဟုတ်ပါ။

run တစ်ကြိမ်စီတွင် လုပ်ဆောင်သည့်အရာများမှာ မိမိတို့၏ ကျန်ရှိပစ္စည်းများ (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) ကို **tmpfs ပေါ်တွင် 3 နာရီ** ကြာပြီးနောက်နှင့် disk ရှိ
`_work/_temp` ပေါ်တွင် 24 နာရီကြာပြီးနောက် ရှင်းလင်းခြင်း၊ 75 မိနစ်ထက် ကြာနေသော
`next-build` ကို ရပ်တန့်ခြင်း (မည်သည့် job မျှ ထိုမျှကြာအောင် မလုပ်ဆောင်ပါ — 2026-08-27 တွင်
GitHub က ၎င်း job ပျောက်ဆုံးသွားပြီဟု သတ်မှတ်ပြီးနောက် တစ်ခုသည် မိနစ် 70 ကြာ ဆက်လက်လုပ်ဆောင်ခဲ့သည်)၊
unit **ရပ်တန့်ထားသော** runner များ၏ 48 နာရီကြာ checkout များကို ရှင်းလင်းခြင်း၊ disk ≥ 85 %၊
memory PSI `full/avg60` ≥ 10 % နှင့် listener အရေအတွက် `MAX_ACTIVE_RUNNERS` ထက် များနေခြင်းတို့ကို
သတိပေးခြင်း (omniroute/အခြား ဟူသော အသေးစိတ်ခွဲခြားချက်နှင့်အတူ) ဖြစ်သည်။ Exit 1 = အာရုံစိုက်ရန်
လိုအပ်သည်ဟု ဆိုလိုသည်။ log ကို ဖတ်ပါ။

75 မိနစ်စည်းမျဉ်းသည် GitHub က လက်လျှော့ပြီးသား job တစ်ခု၏ build ကို မဖမ်းမိပါ။
`Runner.Listener` က ၎င်း၏ job ကို သက်တမ်းမတိုးနိုင်သည့်အခါ `_diag/Runner_*.log` တွင်
`POST request to …/renewjob timed out after 100 seconds` ဟု ပြသပြီး၊ နောက်ဆုံးအောင်မြင်စွာ
သက်တမ်းတိုးပြီး ဆယ်မိနစ်ခန့်အကြာတွင် API က job ကို `completed` (failure) ဟု အစီရင်ခံသော်လည်း
`next-build` သည် ချိတ်ဆက်ထားသော job မရှိဘဲ ဆက်လက်လုပ်ဆောင်နေသည်
(2026-10-18 တွင် #17066 ၏ Build သည် 19:43 ၌ မအောင်မြင်ကြောင်း သတ်မှတ်ခံခဲ့ရသော်လည်း
ငါးမိနစ်အကြာတွင် ၎င်း၏ build က 40 GB ကို ဆက်လက်သိမ်းယူထားဆဲဖြစ်သည်)။ နောက်ဆုံးပေါ်
`_diag/Worker_*.log` ထဲရှိ ref ကို အတည်ပြုပြီးနောက် PID ဖြင့် build tree ကိုသာ SIGTERM ပို့ပါ —
`next-build`, `npm run build`, `build-next-isolated.mjs` နှင့် `_work` worker များဖြစ်သည်။
`Runner.Listener`, `RunnerService.js` သို့မဟုတ် `Runner.Worker` ကို မည်သည့်အခါမျှ
မထိပါနှင့်။ worker က job ကို cancelled ဖြစ်ကြောင်း အစီရင်ခံပြီး listener သည် သူ့ဘာသာသူ
ပြန်လည် online ဖြစ်လာမည်။

## Runner unit များ: KillMode

runner ၏ ပုံသေ `KillMode=process` သည် unit တစ်ခုကို ရပ်တန့်ခြင်း သို့မဟုတ်
ပြန်လည်စတင်ခြင်းပြုသည့်အခါ `Runner.Worker → npm → next-build` ကို ဆက်လက်အလုပ်လုပ်နေစေသည် —
job ချိတ်ဆက်ထားခြင်းမရှိသော orphan build တစ်ခုက RAM နှင့် CPU ကို ဆက်လက်သုံးစွဲနေမည်။
OmniRoute unit တိုင်းတွင် `KillMode=mixed` ပါသော drop-in
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
ရှိသည်။ listener ထံ ဦးစွာ SIGTERM ပို့ပြီး `TimeoutStop` ရောက်ချိန်တွင် cgroup တစ်ခုလုံးထံ

**Self-hosted စွမ်းဆောင်ရည်ကို ထပ်တိုးခြင်းက hosted queue ပြဿနာကို မဖြေရှင်းနိုင်ပါ။** devbox
(`devbox-vm-06-dev002`, 24 vCPU / 54 GB) တွင် runner တစ်ခုကို လက်ခံဆောင်ရွက်နိုင်သော်လည်း agent session များကြောင့် ၎င်း၏ load သည် 20–26 တွင် ရှိနေပြီး၊ agent container တွင် Docker daemon မရှိသည့်အပြင် ပြည့်ကျပ်နေသည့် lane သည်လည်း hosted lane ဖြစ်သည်။ တစ်ချိန်တည်းတွင် `.113` box ၌ နေရာလွတ် 71 GB နှင့် load 5–8 ရှိခဲ့သည်။ ၎င်း၏ ကန့်သတ်ချက်မှာ CPU မဟုတ်ဘဲ အထက်ပါ listener တစ်ခုစီအတွက် memory budget (listener 6 ခုအထိသာ) ဖြစ်သည်။ ကျန်ရှိသော ဖြေရှင်းနည်းများမှာ လုပ်ငန်းစဉ်ပိုင်းဆိုင်ရာ နည်းလမ်းများဖြစ်သည်- campaign PR များကို Mergify queue (`label=queue`) မှတစ်ဆင့် merge လုပ်ပါ၊ batch များသည် PR တစ်ခုစီအတွက် run တစ်ခုနှင့် push တစ်ခုစီအတွက် run တစ်ခုစီ လုပ်ဆောင်မည့်အစား `merge_group` CI run တစ်ခုကို မျှဝေသုံးစွဲသည်။ CodeQL မူလသတ်မှတ်မှု၏ ဘာသာစကားများကို လျှော့ချပြီး `release-acceptance.yml` ကို ၎င်းဖတ်ရှုသည့် ဖိုင်များအလိုက် filter လုပ်ပါ။
