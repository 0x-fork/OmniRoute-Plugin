## Janitor ကို ထည့်သွင်းခြင်း (စက်ပေါ်တွင် တစ်ကြိမ်သာ)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): မိနစ် 30 တိုင်း လုပ်ဆောင်ပြီး /var/log/runner-janitor.log သို့ log ရေးရန်
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` လိုအပ်သည်။ Janitor သည် path တစ်ခုကို မဖယ်ရှားမီ ဖွင့်ထားသော
ဖိုင်များ၏ snapshot တစ်ခုဖြင့် ထို path ကို အသုံးမပြုနေကြောင်း အတည်ပြုသည်။ အဆိုပါ tool မရှိပါက မည်သည့်အရာကိုမျှ မဖယ်ရှားဘဲ
ထိုအခြေအနေကို အသိပေးသည်
(exit 1)။ ပြောင်းလဲမှုတိုင်းကို ဦးစွာ `--dry-run` ဖြင့် စမ်းသပ်ပါ — ၎င်းက လုပ်ဆောင်မည့်အရာကို အတိအကျ
ဖော်ပြပြီး မည်သည့်အရာကိုမျှ မပြောင်းလဲပါ။

တစ်ကြိမ် run တိုင်း လုပ်ဆောင်သည့်အရာများမှာ ကျွန်ုပ်တို့၏ ကျန်ရှိနေသောဖိုင်များ (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) ကို **tmpfs တွင် 3 h** ကြာပြီးနောက်နှင့် disk ရှိ
`_work/_temp` တွင် 24 h ကြာပြီးနောက် ရှင်းလင်းသည်။ 75 min ထက် ကြာနေသော `next-build` ကို ရပ်တန့်သည် (မည်သည့် job မျှ ထိုမျှကြာအောင် မလုပ်ဆောင်ပါ —
2026-08-27 တွင် GitHub က job ကို ဆုံးရှုံးသွားပြီဟု သတ်မှတ်ပြီးနောက်တောင် job တစ်ခုသည် 70 min ကြာ ဆက်လက်လုပ်ဆောင်ခဲ့သည်)။ unit **ရပ်တန့်ထားသော** runner များ၏ 48 h သက်တမ်းရှိ
checkout များကို ရှင်းလင်းသည်။ disk ≥ 85 %၊ memory PSI
`full/avg60` ≥ 10 % နှင့် listener အရေအတွက် `MAX_ACTIVE_RUNNERS` ထက်များသည့်အခါ
omniroute/အခြား ခွဲခြမ်းချက်နှင့်အတူ သတိပေးသည်။ Exit 1 = စစ်ဆေးဆောင်ရွက်ရန် လိုအပ်သည်၊ log ကို ဖတ်ပါ။

## Runner ယူနစ်များ: KillMode

Runner ၏ ပုံသေ `KillMode=process` သည် ယူနစ်တစ်ခုကို ရပ်တန့်ခြင်း သို့မဟုတ် ပြန်လည်စတင်ခြင်း ပြုလုပ်သည့်အခါ `Runner.Worker → npm → next-build` ကို ဆက်လက်အသက်ဝင်နေစေသည် — ထို့ကြောင့် မည်သည့် job နှင့်မျှ ချိတ်ဆက်ထားခြင်းမရှိသော orphan build တစ်ခုက RAM နှင့် CPU ကို ဆက်လက်သုံးစွဲနေမည်ဖြစ်သည်။ OmniRoute ယူနစ်တိုင်းတွင် `KillMode=mixed` ပါဝင်သော drop-in
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
ရှိသည်။ ၎င်းက listener ထံသို့ ပထမဦးစွာ SIGTERM ပို့ပြီး `TimeoutStop` ရောက်သည့်အခါ cgroup တစ်ခုလုံးထံသို့ SIGKILL ပို့သည်။ ၎င်းသည် ယူနစ်၏ နောက်တစ်ကြိမ် ပြန်လည်စတင်မှုတွင် အကျိုးသက်ရောက်မည် — **တစ်ကြိမ်လျှင် runner တစ်ခုသာ၊ idle ဖြစ်နေချိန်တွင်သာ** ပြန်လည်စတင်ပြီး idle စစ်ဆေးမှုနှင့် ပြန်လည်စတင်မှုကို command တစ်ခုတည်းအတွင်း လုပ်ဆောင်ပါ။
