Το αυτοφιλοξενούμενο pool εκτελείται στο μηχάνημα **.113** (`tomni-proxmox-113`). Από τις 2026-10-18, κάθε
runner του OmniRoute έχει **έναν ρόλο**, μία ετικέτα και προϋπολογισμό μνήμης/CPU προσαρμοσμένο σε όσα
μετρήθηκαν για τον φόρτο εργασίας του. Η θέση Turbopack λαμβάνει τους πόρους που χρειάζεται το build· οι
άλλες θέσεις έχουν διαστασιολογηθεί σύμφωνα με τις μετρημένες μέγιστες τιμές τους. Το μηχάνημα κάνει
υπερδέσμευση πόρων μόνο όταν ένα build Turbopack συμπίπτει με ένα build webpack Release-Green και μια
εργασία lint· η swap του host (16 GB) απορροφά αυτήν την αιχμή και, επειδή τα builds των pull request
εκτελούνται σε φιλοξενούμενους runners, η θέση Turbopack παραμένει αδρανής τις περισσότερες φορές:

| runner               | ετικέτα              | ρόλος                                                                                                                                                 | `MemoryHigh` / `MemoryMax` | `CPUQuota`      |
| -------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------- |
| `omniroute-113-5`    | `omni-build`         | Builds Turbopack: `ci.yml` `Build` (μόνο push/dispatch), Docker amd64, `npm-publish`, `nightly-v4-build`, `preview-artifact`, το νυχτερινό build a11y | 56 GB / 60 GB (swap 0)     | 1600 %          |
| `omniroute-113-6`    | `omni-release`       | Release-Green (`release-green` + `main-green`), build webpack                                                                                         | 20 GB / 24 GB (swap 4 GB)  | 800 %           |
| `omniroute-113-2`    | `omni-light`         | νυχτερινές εργασίες (Schemathesis, promptfoo, garak, k6, εκκίνηση a11y) και `quality.yml` `lint-guard`                                                | 12 GB / 16 GB (swap 4 GB)  | 600 %           |
| `omniroute-113`      | `omni-light`         | ίδιο pool με το παραπάνω                                                                                                                              | 8 GB / 12 GB               | 400 %           |
| OmniHeuris, OmniMind | (τα αποθετήριά τους) | μόνο Dependabot (μέγιστη τιμή 155 MB για το καθένα, 2026-10-18)                                                                                       | 4 GB / 6 GB                | 200 % το καθένα |

| --------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

Τα όρια βρίσκονται στο `/etc/systemd/system/actions.runner.<…>.service.d/override.conf` κάθε μονάδας
(οι προηγούμενες τιμές διατηρούνται ως `override.conf.bak-20261018`) και εφαρμόστηκαν ζωντανά με
`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` — χωρίς επανεκκίνηση, επομένως
δεν επηρεάστηκε καμία εργασία που βρισκόταν σε εξέλιξη. Οι ετικέτες αλλάζουν μέσω του API των runners
(`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`), επίσης ζωντανά.

## Εγκατάσταση του janitor (μία φορά, στον διακομιστή)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): κάθε 30 λεπτά, καταγραφή στο /var/log/runner-janitor.log
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

Το `lsof` είναι απαραίτητο: το janitor επιβεβαιώνει ότι μια διαδρομή είναι ανενεργή με ένα στιγμιότυπο των ανοιχτών
αρχείων πριν την αφαιρέσει, ενώ χωρίς το εργαλείο δεν αφαιρεί τίποτα και το αναφέρει
(exit 1). Δοκιμάστε πρώτα οποιαδήποτε αλλαγή με `--dry-run` — εμφανίζει ακριβώς τι θα
έκανε και δεν τροποποιεί τίποτα.

Τι κάνει σε κάθε εκτέλεση: καθαρίζει τα δικά μας υπολείμματα (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) μετά από **3 ώρες στο tmpfs** και 24 ώρες στο
`_work/_temp` του δίσκου· τερματίζει ένα `next-build` παλαιότερο από 75 λεπτά (καμία εργασία δεν εκτελείται για τόσο πολύ — στις
2026-08-27 μία εκτελούνταν για 70 λεπτά αφού το GitHub είχε δηλώσει ότι η εργασία της χάθηκε)· διαγράφει checkouts παλαιότερα των 48 ωρών
από runners των οποίων η μονάδα είναι **σταματημένη**· ειδοποιεί όταν η χρήση δίσκου είναι ≥ 85 %, το PSI μνήμης
`full/avg60` είναι ≥ 10 % και υπάρχουν περισσότεροι listeners από το `MAX_ACTIVE_RUNNERS` (με
ανάλυση omniroute/other). Exit 1 = απαιτείται προσοχή· διαβάστε το αρχείο καταγραφής.

Ο κανόνας των 75 λεπτών δεν εντοπίζει ένα build του οποίου την εργασία το GitHub έχει ήδη εγκαταλείψει. Όταν το
`Runner.Listener` δεν μπορεί να ανανεώσει την εργασία του, το `_diag/Runner_*.log` εμφανίζει
`POST request to …/renewjob timed out after 100 seconds`, το API αναφέρει την εργασία ως `completed`
(αποτυχία) περίπου δέκα λεπτά μετά την τελευταία επιτυχημένη ανανέωση και το `next-build` συνεχίζει να εκτελείται
χωρίς συσχετισμένη εργασία (2026-10-18: το Build του #17066 απέτυχε στις 19:43 και το build του εξακολουθούσε
να δεσμεύει 40 GB πέντε λεπτά αργότερα). Επιβεβαιώστε το ref στο νεότερο `_diag/Worker_*.log` και, στη συνέχεια,
στείλτε SIGTERM μόνο στο δέντρο διεργασιών του build μέσω PID — `next-build`, `npm run build`, `build-next-isolated.mjs` και
τους workers του `_work`. Μην αγγίζετε ποτέ τα `Runner.Listener`, `RunnerService.js` ή `Runner.Worker`: ο
worker αναφέρει την εργασία ως ακυρωμένη και ο listener επανέρχεται online μόνος του.

## Μονάδες runner: KillMode

Το προεπιλεγμένο `KillMode=process` του runner αφήνει το `Runner.Worker → npm → next-build`
ενεργό όταν μια μονάδα σταματά ή επανεκκινείται — ένα ορφανό build συνεχίζει να καταναλώνει RAM και
CPU χωρίς συσχετισμένη εργασία. Κάθε μονάδα OmniRoute διαθέτει ένα drop-in
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
με `KillMode=mixed`: SIGTERM πρώτα στον listener και SIGKILL σε ολόκληρο το cgroup κατά το
`TimeoutStop`. Ενεργοποιείται στην επόμενη επανεκκίνηση της μονάδας — επανεκκινήστε **έναν runner κάθε
φορά, μόνο όταν είναι ανενεργός**, με τον έλεγχο αδράνειας και την επανεκκίνηση στην ίδια εντολή.

## Κανόνες λειτουργίας

- **Μία μεταγλώττιση Turbopack κάθε φορά — επιβάλλεται μέσω label.** Κάθε job που εκτελεί ένα πλήρες
  `next build` με Turbopack στοχεύει το `[self-hosted, omni-build]`, και μόνο το **`omniroute-113-5`** φέρει αυτό
  το label: `ci.yml` `Build`, `npm-publish.yml` `publish`, `nightly-v4-build`, `preview-artifact`,
  η νυχτερινή μεταγλώττιση a11y (#16853) και το **amd64** του `docker-publish.yml` (webpack μέσα στο BuildKit —
  το Turbopack κατέρρευσε εκεί, run 33253576569). Το σκέλος Docker για arm64 παραμένει στο `ubuntu-24.04-arm`.
  Το amd64 του `docker-publish` μοιράζεται το concurrency group `heavy-build-main` με το `Build` του `ci.yml`
  (`cancel-in-progress: false`). Το Docker Engine πρέπει να βρίσκεται στο `omniroute-113-5`. Δεύτερο slot για Turbopack
  δεν χωρά στα 78 GB (2 × 33–37 GB συν τα υπόλοιπα φορτία του μηχανήματος)· δεύτερο slot είναι ασφαλές μόνο για
  μεταγλωττίσεις webpack.
- **Τα Builds των pull request εκτελούνται σε hosted runner (2026-10-18).** Το `Build` του `ci.yml` φτάνει στο `omni-build` μόνο για
  `push` και `workflow_dispatch`· κάθε `Build` για `pull_request` (ίδιας προέλευσης ή fork) και `merge_group`
  εκτελείται στο `ubuntu-latest` με webpack. Όταν κάθε PR ίδιας προέλευσης δρομολογούνταν στο slot, ένα Build με Turbopack
  το κρατούσε για 29–58 λεπτά, 18 Builds έμεναν στην ουρά έως και 18 ώρες, και το push Build της ίδιας της γραμμής release
  πήρε το slot μία φορά σε 40 jobs. Στο hosted περιβάλλον, το ίδιο PR Build διαρκεί 8–12 λεπτά παράλληλα με τα άλλα
  jobs του PR. Το Turbopack, ο bundler που διανέμει το `npm-publish`, συνεχίζει να δοκιμάζεται στη γραμμή release μέσω της
  νυχτερινής μεταγλώττισης a11y του προεπιλεγμένου branch (04:41 UTC), μέσω κάθε Build από push ή dispatch που
  φτάνει στο slot, καθώς και μέσω του ίδιου του `npm-publish`. Το `tests/unit/build/heavy-build-queue.test.ts`
  κατοχυρώνει την πύλη τεσσάρων συνθηκών.
- **Ποτέ μην ορίζετε το slot του Turbopack κάτω από τις μετρημένες ανάγκες του.** Στις 2026-10-18 στις 18:06 το slot
  μειώθηκε από 56G/60G σε 40G/44G για να δημιουργηθεί χώρος για το `omni-release`. Η φάση μεταγλώττισης παρέμεινε στο
  `MemoryHigh` καθ’ όλη τη διάρκειά της (memory PSI `full` 30–43 %), και το `Runner.Listener`, το οποίο
  μοιράζεται το cgroup, δεν μπορούσε να ανανεώσει το job του. Η ρύθμιση 56G/60G του ιδιοκτήτη από τις 2026-10-17 επανήλθε την
  ίδια ημέρα. Κάτω από αυτήν την τιμή η μεταγλώττιση δεν αποτυγχάνει· καταπονείται από συνεχή εναλλαγή μνήμης και το job χάνεται.
- **Το Release-Green έχει το δικό του slot (2026-10-18).** Μέχρι τότε και οι δύο επικυρώσεις Release-Green εκτελούνταν
  στο `omni-build`: σε κάθε push (~10/ώρα, 97 από 100 εκτελέσεις push ακυρώθηκαν ενώ βρίσκονταν σε εξέλιξη μέσα σε μία ημέρα)
  και σε τρεις πλήρεις σαρώσεις διάρκειας ~2 ωρών ημερησίως (η σάρωση των 05:29 περίμενε 6 ώρες για το slot) — το μοναδικό slot
  μεταγλώττισης είχε πολλαπλάσια υπερδέσμευση και τα Builds των PR ίδιας προέλευσης περίμεναν για ώρες.
  Τα `release-green` και `main-green` στοχεύουν πλέον το `omni-release` (μόνο το `omniroute-113-6`) με
  `OMNIROUTE_USE_TURBOPACK=0`, και μια εκτέλεση που έχει ξεκινήσει δεν ακυρώνεται πλέον από νεότερο push (το
  slot αναμονής εξακολουθεί να συμπτύσσει την καταιγίδα εκτελέσεων). Το `tests/unit/build/runner-capacity-routing.test.ts`
  κατοχυρώνει τη δρομολόγηση, τη μετάβαση σε webpack και το ότι τίποτα στο `omni-release` δεν μεταγλωττίζεται με Turbopack.
- **Ελαφρύ pool: `omni-light`.** Τα `omniroute-113` και `omniroute-113-2` εκτελούν τα νυχτερινά jobs που χρειάζονται
  ένα `next build` μόνο για το backend (~5–6 GB· webpack), καθώς και το `lint-guard` του `quality.yml`. Το `omniroute-113`
  είχε `MemoryHigh=4G` έως τις 2026-10-18 — η μεταγλώττιση promptfoo προχωρούσε ανακτώντας συνεχώς μνήμη επί 54 λεπτά
  εκεί· τα 8 GB εξαλείφουν τον περιορισμό.
- **Λιγότεροι listeners επίτηδες.** Τέσσερα units του OmniRoute απενεργοποιήθηκαν στις 2026-08-29 — κάθε επιπλέον
  listener αποτελεί έναν ακόμη καταναλωτή του παραπάνω προϋπολογισμού μνήμης. Το ανώτατο όριο του janitor είναι 6 (`MAX_ACTIVE_RUNNERS=6` στο cron): μετρά
  κάθε `Runner.Listener` στο μηχάνημα, ενώ τα OmniHeuris + OmniMind προσθέτουν δύο στα δικά μας τέσσερα.
- **Ποτέ μην καθαρίζετε τα `/tmp` ή `_work` χειροκίνητα όσο οποιοσδήποτε runner είναι απασχολημένος.** Ένας
  έλεγχος και κατόπιν διαγραφή, με κενό μεταξύ των δύο ενεργειών, ήταν ο λόγος που ένα ενεργό Build job έχασε το
  `_work` του στις 2026-08-27. Ο janitor πραγματοποιεί τον έλεγχο και την αφαίρεση σε ένα βήμα·
  αφήστε τον να το κάνει.
- Η διακοπή ενός runner ενώ εκτελεί job ακυρώνει το job (παρατηρήθηκε σε πραγματική εκτέλεση): χρησιμοποιήστε `systemctl stop` μόνο
  όταν ο listener του δεν έχει θυγατρική διεργασία `Runner.Worker` — και κάντε το με μία εντολή.
- Τα workflows δεν πρέπει να αποθηκεύουν artefacts στο `/tmp` (βρίσκεται στη RAM). Πραγματοποιείτε λήψη στο
  `$RUNNER_TEMP` (στον δίσκο, ανά runner) — το artefact `next-build` μεγέθους 1.3 GB χρειάστηκε 27–32
  λεπτά για να αποθηκευτεί στο tmpfs και 2 λεπτά για να μεταφορτωθεί από τον δίσκο.
- Το VPS `.15` προορίζεται μόνο για homologation — δεν εκτελεί ποτέ CI runners.

## Φιλοξενούμενη λωρίδα (εκτελεστές που φιλοξενούνται στο GitHub)

Ο λογαριασμός βρίσκεται στο πρόγραμμα **Pro**: **40 ταυτόχρονες φιλοξενούμενες εργασίες**, οι οποίες μοιράζονται μεταξύ κάθε ελέγχου PR,
κάθε ροής εργασιών που ενεργοποιείται από push και της προεπιλεγμένης ρύθμισης του CodeQL. Μετρήθηκε στις 2026-10-18 κατά τη διάρκεια μιας
εκστρατείας συγχωνεύσεων (~10 συγχωνεύσεις/ώρα στο `release/v3.8.52`): δημιουργήθηκαν **2.500 εκτελέσεις ροών εργασιών σε
24 ώρες**, έγιναν 44 push στον κλάδο μέσα σε 6 ώρες και **106 φιλοξενούμενες εργασίες μπήκαν σε ουρά**, ενώ οι έλεγχοι PR περίμεναν για
ώρες και τα PR συγχωνεύονταν χωρίς αυτούς. Εννέα ροές εργασιών ενεργοποιούνταν σε κάθε push στον κλάδο:

| ανά push στο `release/v*`                   | φιλοξενούμενες εργασίες | αποτέλεσμα υπό τον καταιγισμό                                       | από τις 2026-10-18                                                                 |

**Η μεγαλύτερη χωρητικότητα αυτοφιλοξενούμενων εκτελεστών δεν διορθώνει την ουρά φιλοξενούμενων εργασιών.** Το devbox
(`devbox-vm-06-dev002`, 24 vCPU / 54 GB) θα μπορούσε να φιλοξενήσει έναν εκτελεστή, αλλά οι συνεδρίες των agent ήδη
διατηρούν το φορτίο του στο 20–26, το container των agent δεν διαθέτει daemon του Docker και η κορεσμένη λωρίδα είναι
η φιλοξενούμενη. Το μηχάνημα `.113` είχε 71 GB ελεύθερα και φορτίο 5–8 την ίδια στιγμή· ο περιορισμός του
είναι ο παραπάνω προϋπολογισμός μνήμης ανά listener (ανώτατο όριο 6 listener), όχι η CPU. Οι υπόλοιποι μοχλοί
αφορούν τη διαδικασία: ενσωματώστε τα PR της εκστρατείας μέσω της ουράς Mergify (`label=queue`, οι παρτίδες μοιράζονται
μία εκτέλεση CI `merge_group` αντί για μία εκτέλεση ανά PR συν μία ανά push), περιορίστε τις γλώσσες της
προεπιλεγμένης ρύθμισης του CodeQL και φιλτράρετε το `release-acceptance.yml` βάσει των αρχείων που διαβάζει.
