Пул із власним хостингом працює на сервері **.113** (`tomni-proxmox-113`). Починаючи з 2026-10-18, кожен
ранер OmniRoute має **одну роль**, одну мітку та бюджет пам’яті/CPU, визначений за виміряним
навантаженням. Слот Turbopack отримує ресурси, потрібні для збірки; інші слоти налаштовані відповідно до їхніх
виміряних пікових значень. Надлишкове виділення ресурсів на сервері виникає лише тоді, коли збірка Turbopack збігається зі збіркою webpack
Release-Green і завданням lint; це компенсується свопом хоста (16 GB), а оскільки збірки для запитів на злиття виконуються
на хостингових раннерах, слот Turbopack більшу частину часу простоює:

| ранер                | мітка              | роль                                                                                                                                            | `MemoryHigh` / `MemoryMax` | `CPUQuota`        |
| -------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | ----------------- |
| `omniroute-113-5`    | `omni-build`       | Збірки Turbopack: `ci.yml` `Build` (лише push/dispatch), Docker amd64, `npm-publish`, `nightly-v4-build`, `preview-artifact`, нічна збірка a11y | 56 GB / 60 GB (своп 0)     | 1600 %            |
| `omniroute-113-6`    | `omni-release`     | Release-Green (`release-green` + `main-green`), збірка webpack                                                                                  | 20 GB / 24 GB (своп 4 GB)  | 800 %             |
| `omniroute-113-2`    | `omni-light`       | нічні завдання (Schemathesis, promptfoo, garak, k6, запуск a11y) і `quality.yml` `lint-guard`                                                   | 12 GB / 16 GB (своп 4 GB)  | 600 %             |
| `omniroute-113`      | `omni-light`       | той самий пул, що й вище                                                                                                                        | 8 GB / 12 GB               | 400 %             |
| OmniHeuris, OmniMind | (їхні репозиторії) | лише Dependabot (пікове значення 155 MB для кожного, 2026-10-18)                                                                                | 4 GB / 6 GB                | 200 % для кожного |

| ресурс    | значення                                   | що це означає для планування                                                                                                                                                                                                                                                                                                                                                                                |
| --------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RAM / CPU | **78 GB / 32 ядра**                        | пікове споживання продуктивної збірки Turbopack без обмежень становило 49 GB (`tests/unit/ci-build-bundler-webpack.test.ts`); у Next 16.3.8 лише фаза компіляції утримує ~40 GB (36 GB RSS у `next-build` плюс 17 воркерів завантажувача по 3 GB, виміряно 2026-10-18); збірка webpack споживає ~14–16 GB. | `/tmp`    | **12 GB tmpfs = RAM**                      | усе, що зберігається там, займає пам’ять; залишки видаляються через 3 години                                                                                                                                                                                                                                                                                                                                |
| CPU       | спостерігалося навантаження 60 на 32 ядрах | до введення квот одна збірка Turbopack (~1166 % CPU) разом із набором тестів покриття на тому самому сервері позбавляли інші слухачі ресурсів для сигналів активності (`The self-hosted runner lost communication`, #16853)                                                                                                                                                                                 |

Обмеження зберігаються для кожного юніта у `/etc/systemd/system/actions.runner.<…>.service.d/override.conf`
(попередні значення збережено як `override.conf.bak-20261018`) і були застосовані безпосередньо командою
`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` — без перезапуску, тому жодне
виконуване завдання не було перервано. Мітки змінюються через API ранерів
(`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`), також без перезапуску.

## Установіть засіб очищення (одноразово, на сервері)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): кожні 30 хв, журнал у /var/log/runner-janitor.log
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` є обов’язковим: перед видаленням засіб очищення перевіряє, що шлях не використовується, за допомогою одного знімка відкритих
файлів, а без цього інструмента нічого не видаляє та повідомляє про це
(код виходу 1). Спочатку перевіряйте будь-яку зміну з `--dry-run` — цей режим точно показує, що було б
зроблено, і нічого не змінює.

Що він робить під час кожного запуску: видаляє наші власні залишкові файли (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) через **3 год на tmpfs** і через 24 год на диску в
`_work/_temp`; завершує `next-build`, старіший за 75 хв (жодне завдання не виконується так довго —
2026-08-27 одне з них працювало 70 хв після того, як GitHub оголосив завдання втраченим); видаляє робочі копії,
старіші за 48 год, для раннерів, чиї юніти **зупинено**; сповіщає, коли використання диска ≥ 85 %, PSI пам’яті
`full/avg60` ≥ 10 % або кількість слухачів перевищує `MAX_ACTIVE_RUNNERS` (із розподілом на
omniroute/інші). Код виходу 1 = потрібна увага; перегляньте журнал.

Правило 75 хв не виявляє збірку, завдання якої GitHub уже припинив очікувати. Коли
`Runner.Listener` не може поновити своє завдання, `_diag/Runner_*.log` містить
`POST request to …/renewjob timed out after 100 seconds`, API повідомляє, що завдання `completed`
(невдача), приблизно через десять хвилин після останнього успішного поновлення, а `next-build` продовжує працювати
без прив’язаного завдання (2026-10-18: збірка #17066 завершилася невдало о 19:43, але її процес збірки все ще
утримував 40 ГБ через п’ять хвилин). Перевірте ref у найновішому `_diag/Worker_*.log`, а потім
надішліть SIGTERM лише дереву процесів збірки за PID — `next-build`, `npm run build`, `build-next-isolated.mjs` і
воркерам `_work`. Ніколи не чіпайте `Runner.Listener`, `RunnerService.js` або `Runner.Worker`: воркер
повідомить, що завдання скасовано, а слухач самостійно повернеться в онлайн.

## Юніти раннерів: KillMode

Стандартний для раннера `KillMode=process` залишає `Runner.Worker → npm → next-build`
працювати після зупинення або перезапуску юніта — осиротілий процес збірки продовжує споживати оперативну пам’ять і
процесорний час без прив’язаного завдання. Кожен юніт OmniRoute має додатковий конфігураційний файл
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
з `KillMode=mixed`: спочатку надсилається SIGTERM слухачу, а під час
`TimeoutStop` — SIGKILL усій cgroup. Налаштування набуде чинності після наступного перезапуску юніта — перезапускайте **по одному раннеру
за раз і лише коли він неактивний**, виконуючи перевірку неактивності та перезапуск однією командою.

## Правила експлуатації

- **Лише одна збірка Turbopack одночасно — це забезпечується міткою.** Кожне завдання, що виконує повну
  збірку Turbopack через `next build`, націлене на `[self-hosted, omni-build]`, і лише **`omniroute-113-5`** має цю
  мітку: `ci.yml` `Build`, `npm-publish.yml` `publish`, `nightly-v4-build`, `preview-artifact`,
  нічна a11y-збірка (#16853) та **amd64** у `docker-publish.yml` (webpack усередині BuildKit —
  Turbopack аварійно завершився там, запуск 33253576569). Гілка Docker для arm64 залишається на `ubuntu-24.04-arm`.
  amd64 у `docker-publish` використовує спільну групу конкурентності `heavy-build-main` із `Build` у `ci.yml`
  (`cancel-in-progress: false`). Docker Engine має бути на `omniroute-113-5`. Другий слот Turbopack
  не вміщується в 78 ГБ (2 × 33–37 ГБ плюс решта навантаження машини); другий слот безпечний лише для
  збірок webpack.
- **Збірки pull request виконуються на хмарних раннерах (2026-10-18).** `Build` у `ci.yml` потрапляє на `omni-build` лише для
  `push` і `workflow_dispatch`; кожна збірка `pull_request` (із власного репозиторію або форка) та `merge_group`
  виконується на `ubuntu-latest` із webpack. Коли кожен PR із власного репозиторію спрямовувався до слота, збірка Turbopack
  займала його на 29–58 хв, 18 збірок чекали в черзі до 18 год, а власна push-збірка гілки релізу
  отримала слот один раз за 40 завдань. На хмарному раннері та сама збірка PR триває 8–12 хв паралельно з іншими
  завданнями цього PR. Turbopack, бандлер, який постачається через `npm-publish`, і надалі перевіряється на гілці релізу
  нічною a11y-збіркою гілки за замовчуванням (04:41 UTC), кожною push- або dispatch-збіркою, яка
  отримує слот, а також самим `npm-publish`. `tests/unit/build/heavy-build-queue.test.ts`
  фіксує умову з чотирьох пунктів.
- **Ніколи не виділяйте слоту Turbopack менше за виміряну потребу.** 2026-10-18 о 18:06 ліміти слота було
  знижено з 56G/60G до 40G/44G, щоб звільнити місце для `omni-release`. Фаза компіляції перебувала на рівні
  `MemoryHigh` протягом усього запуску (показник `full` для memory PSI — 30–43 %), а `Runner.Listener`, який
  використовує ту саму cgroup, не зміг поновити своє завдання. Власні значення 56G/60G від 2026-10-17 було відновлено
  того ж дня. За нижчих значень збірка не завершується помилкою; вона витрачає ресурси на постійне вивантаження та підвантаження пам’яті,
  і завдання втрачається.
- **Release-Green має власний слот (2026-10-18).** До цього обидві перевірки Release-Green виконувалися
  на `omni-build`: під час кожного push (~10/год, 97 зі 100 push-запусків було скасовано посеред виконання за один день)
  і трьох повних прогонів тривалістю ~2 год щодня (прогін о 05:29 чекав на слот 6 год) — єдиний слот збірки
  був перевантажений у кілька разів, а збірки PR із власного репозиторію чекали годинами.
  `release-green` і `main-green` тепер націлені на `omni-release` (лише `omniroute-113-6`) з
  `OMNIROUTE_USE_TURBOPACK=0`, а розпочатий запуск більше не скасовується новішим push (слот очікування
  усе ще згортає шквал запусків). `tests/unit/build/runner-capacity-routing.test.ts`
  фіксує маршрутизацію, перемикання на webpack і те, що на `omni-release` нічого не збирається за допомогою Turbopack.
- **Пул легких завдань: `omni-light`.** `omniroute-113` і `omniroute-113-2` виконують нічні завдання, яким потрібна
  лише серверна збірка через `next build` (~5–6 ГБ; webpack), а також `lint-guard` у `quality.yml`. На `omniroute-113`
  до 2026-10-18 було встановлено `MemoryHigh=4G` — збірка promptfoo протягом 54 хв постійно звільняла пам’ять,
  щоб продовжувати роботу; 8 ГБ усувають це обмеження.
- **Менше слухачів — навмисно.** Чотири модулі OmniRoute було вимкнено 2026-08-29 — кожен додатковий
  слухач є ще одним споживачем наведеного вище бюджету пам’яті. Граничне значення для прибиральника — 6 (`MAX_ACTIVE_RUNNERS=6` у cron): він рахує
  кожен `Runner.Listener` на машині, а OmniHeuris + OmniMind додають ще два до наших чотирьох.
- **Ніколи не очищуйте `/tmp` або `_work` вручну, поки хоча б один раннер зайнятий.**
  Перевірка з подальшим видаленням після паузи між цими діями призвела до того, що активне завдання Build втратило свій
  `_work` 2026-08-27. Прибиральник виконує перевірку та видалення як одну операцію;
  залиште це йому.
- Зупинка раннера посеред завдання скасовує завдання (спостерігалося наживо): виконуйте `systemctl stop`, лише
  коли його слухач не має дочірнього процесу `Runner.Worker`, — і робіть це однією командою.
- Робочі процеси не повинні зберігати артефакти в `/tmp` (він розташований в оперативній пам’яті). Завантажуйте їх у
  `$RUNNER_TEMP` (на диску, окремо для кожного раннера) — завантаження артефакту `next-build` розміром 1,3 ГБ на tmpfs тривало 27–32
  хвилини, а вивантаження з диска — 2 хвилини.
- VPS `.15` призначений лише для омологації — CI-раннери на ньому ніколи не запускаються.

## Хостингова смуга (ранери, розміщені на GitHub)

Обліковий запис має план **Pro**: **40 одночасних хостингових завдань**, спільних для всіх перевірок PR,
усіх робочих процесів, що запускаються надсиланням змін, і стандартного налаштування CodeQL. За вимірами 2026-10-18 під час
кампанії злиттів (~10 злиттів/годину в `release/v3.8.52`): **2 500 запусків робочих процесів створено за
24 год**, 44 надсилання змін до гілки за 6 год, **106 хостингових завдань у черзі**, тоді як перевірки PR чекали
годинами, а PR зливали без них. Дев’ять робочих процесів запускалися під час кожного надсилання змін до гілки:

**Збільшення власних обчислювальних потужностей не усуває чергу хостингових завдань.** На devbox
(`devbox-vm-06-dev002`, 24 vCPU / 54 GB) можна було б розмістити ранер, але сеанси агентів уже
утримують його навантаження на рівні 20–26, контейнер агента не має демона Docker, а перевантаженою є саме
хостингова смуга. На машині `.113` у той самий момент було 71 GB вільного місця та навантаження 5–8; її обмеженням
є наведений вище бюджет пам’яті на кожен слухач (максимум 6 слухачів), а не CPU. Решта важелів
є процесними: інтегрувати PR кампанії через чергу Mergify (`label=queue`, пакети спільно використовують
один запуск CI `merge_group` замість одного запуску на PR плюс одного на кожне надсилання змін), скоротити перелік мов
стандартного налаштування CodeQL і фільтрувати `release-acceptance.yml` за файлами, які він читає.
